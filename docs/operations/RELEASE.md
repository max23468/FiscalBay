# Test e pubblicazione

Ciclo dalla PR a Production. Ingressi, incidenti, capacità e ripristino sono nelle [operazioni](OPERATIONS.md). Il ciclo cambia soltanto per un errore riprodotto o su richiesta dell'owner, non per affinamenti ([D279](../decisions/DECISION_REGISTER.md)): ogni modifica costa una qualifica e invalida il riuso.

## Controlli proporzionati

`pnpm verify:changed` usa lo stesso classificatore della CI e, prima del gate, lo stesso controllo della versione di `Verify` rispetto a `origin/develop`. Sulle PR il confronto parte dalla base e arriva al commit di merge provato, così una testa che non contiene la base non riporta come proprie le modifiche entrate nel frattempo; sui push a `develop` parte dall'ultimo deploy test riuscito, così una run annullata da un push successivo o un deploy fallito restano nel diff della run seguente. Se dopo quel deploy una run è riuscita con modifiche che non chiedono un deploy, come prove, strumenti o documenti, il confronto parte da lei: ciò che ha già qualificato non si ripete a ogni push fino al deploy seguente. Senza un deploy riuscito fra le run recenti, e negli avvii manuali, vale il gate completo. Il candidato Production forza sempre il collaudo completo.

Il classificatore sceglie uno di cinque livelli, le prove browser e il deploy test ([D190](../decisions/DECISION_REGISTER.md), [D192](../decisions/DECISION_REGISTER.md)). Ogni livello esegue uno script di `package.json`, unica definizione della sequenza, e comprende il precedente: `verify:tooling` comprende `verify:documents`, `verify:unit` comprende `verify:tooling`, `verify:build` e `verify` comprendono `verify:unit` e chiudono con la build test, l'artefatto caricato. Il riepilogo della run riporta livello, browser, deploy e moduli mutation.

| Livello | File | Verifica | Browser, build e deploy |
|---|---|---|---|
| Documenti | Markdown, compresi roadmap e documenti di prodotto, engineering e operations; archivio documentale, soltanto il giorno di una versione nel changelog | `pnpm verify:documents`: copy, link, ancore, tabelle e decisioni | Nessuno |
| Strumenti | Istruzioni degli agenti (`AGENTS.md`, `CLAUDE.md`), script operativi e loro test, workflow e Action, `.gitignore`, configurazioni di formato, lint, Knip, mutation e benchmark; un `package.json` che cambia soltanto script non eseguiti da build, deploy o installazione prende il livello più leggero che li esegue | `pnpm verify:tooling`: anche tipi generati, repository, catalogo pagine, test degli script, formato, lint e Knip; Actionlint per i workflow | Nessuno implicito; qualifica remota della procedura quando necessaria nel mandato |
| Test applicativi | `test/`, configurazioni Vitest | `pnpm verify:unit`: anche typecheck e copertura | Nessuno |
| Build | Prove browser (`e2e/`, `playwright.config.ts`, runner e anteprima locale), controllo del bundle, soli valori `bindings.text(...)` delle `vars` del Worker test | `pnpm verify:build`: anche build test | Le prove browser eseguono i browser senza deploy; i valori del test distribuiscono con il collaudo remoto, senza browser della PR; il bundle nessuno dei due |
| Completo | Runtime, configurazione applicativa e dei Worker, dipendenze, migration, file sconosciuti, diff vuoto o candidato | `pnpm verify`: anche React Doctor e build live | Browser secondo le aree, deploy test |

Gli script ammessi fra gli strumenti e nel livello build sono elencati in `scripts/classify-changes.mjs`; un nuovo script resta nel livello completo finché non viene aggiunto. Per `cloudflare.config.ts` il classificatore confronta le due versioni: basta un nome, una riga aggiunta o tolta, un binding, una risorsa, un dominio, un commento o un valore `live` diverso, oppure una versione non leggibile, per il livello completo. Dopo ogni deploy test lo smoke e le pagine `@remote` girano comunque.

Ogni modulo applicativo dichiara in `scripts/classify-changes.mjs` che cosa prova ([D265](../decisions/DECISION_REGISTER.md)): un'area in `moduleAreas`, oppure un elenco vuoto se nessuna pagina lo mostra (code, cron, log, tempi), oppure la suite completa in `sharedModules` (shell, copy, componenti comuni, aggregatori). Un modulo senza dichiarazione ferma `pnpm test:scripts`: nulla prova tutto per dimenticanza. Una route prende l'area dal nome e si aggiungono le aree delle route che importano direttamente il modulo; gli import transitivi non contano, perché i moduli di dominio raggiungono quasi tutte le route attraverso gli aggregatori. Un modulo senza pagine non apre browser, se nessuna route lo importa direttamente.

Una selezione per area esegue le prove `@smoke`, le visite del catalogo con il tag `@pages-<area>` e le prove funzionali il cui titolo appartiene all'area. Una spec modificata seleziona se stessa per nome; `pages.spec` si visita allora con una sola combinazione di larghezza e tema. Gli altri file di `e2e/` e la configurazione di Playwright eseguono tutte le prove ([D195](../decisions/DECISION_REGISTER.md)); runner, anteprima e D1 locale, che preparano ogni prova allo stesso modo, il nucleo `@smoke` in entrambi i browser. Il controllo dell'evidenza del candidato sta in `scripts/browser-evidence.mjs`, fra gli strumenti, perché non esegue prove. WebKit gira quando cambia ciò che il browser disegna o esegue: una modifica di soli moduli server, `.server.ts`, `app/domain/` o `app/integrations/`, resta in Chromium ([D266](../decisions/DECISION_REGISTER.md)); la qualifica prova sempre entrambi. Le dipendenze si pesano dal manifest ([D267](../decisions/DECISION_REGISTER.md)): i soli strumenti di sviluppo eseguono il gate completo senza browser né deploy, quelle dell'artefatto (`dependencies` e gli strumenti di build, Vite, TypeScript, Tailwind, React Router, Playwright) il nucleo `@smoke` e il deploy test; altri campi del manifest provano tutto. I test del classificatore verificano la scelta del livello e delle prove, non l'elenco dei comandi.

`pnpm verify:changed` è il controllo ordinario, senza browser ([D268](../decisions/DECISION_REGISTER.md), [D298](../decisions/DECISION_REGISTER.md)): in locale esegue lo script statico del livello (`verify:documents`, `verify:tooling`, `verify:static` con strumenti e typecheck, `verify:static:full` che aggiunge React Doctor) e poi i test Vitest collegati al diff con `pnpm test:related`. Un diff fuori da `app/`, `workers/` e `test/` che i test leggono, come manifest, configurazioni o changelog, esegue l'intera suite con `pnpm test`; prove browser e strumenti non toccano Vitest. Copertura e build restano alla CI, che esegue lo script del livello sul diff della PR. `pnpm verify:browser` esegue le prove scelte dal classificatore in Chromium, soltanto se la modifica cambia ciò che il browser disegna o esegue: con soli moduli server le lascia alla CI. In locale Playwright usa un worker ogni 6 GiB di memoria, al più quattro come in CI ([D311](../decisions/DECISION_REGISTER.md)). Con il collaudo dell'account sulla preview locale, quando la modifica tocca accesso, Ordini o Negozi, è ciò che serve prima di una PR. WebKit resta alla CI, che lo esegue in parallelo su otto macchine in meno tempo di quanto richieda sul Mac ([D315](../decisions/DECISION_REGISTER.md)); la suite completa resta ai job della CI, che la eseguono sulla build da distribuire ([D205](../decisions/DECISION_REGISTER.md)); `pnpm test:e2e` e `pnpm verify:full` restano per una diagnosi esplicita. Sul Mac la preview delle prove usa una porta ricavata dal percorso del worktree, così due sessioni non si contendono la stessa; in CI resta la 5186 ed `E2E_PORT` la sceglie esplicitamente. In locale `verify:changed` registra nella cartella Git del worktree il tree verde del checkout, file non tracciati compresi: la verifica successiva confronta il checkout con quel tree e prova soltanto le modifiche intervenute, senza ripetere nulla se non ce ne sono; `--all` riparte da `origin/develop` ([D195](../decisions/DECISION_REGISTER.md)). La CI resta la qualifica completa della PR; dopo un verde locale una correzione minima non richiede un gate locale completo.

Se il diff aggiunge migration non additive, il comando stampa la riga `reviewed-migrations` da inserire, dopo l'esame, nel corpo della PR prima di aprirla. Una migration già presente nella base, modificata anche solo in un commento o eliminata, ferma il classificatore: il deploy confronta le migration applicate con la versione distribuita e rifiuta ogni differenza, come è successo alla [#495](https://github.com/max23468/FiscalBay/pull/495) con il deploy test annullato prima delle migration. Una correzione passa da una nuova migration o dalla documentazione.

Gate e browser hanno ricevute indipendenti, `verify-changed.json` e `verify-browser.json`, nella cartella Git del worktree ([D285](../decisions/DECISION_REGISTER.md)), con tree, durata in secondi e livello o browser eseguiti. Il verde del primo non attesta il secondo: i browser confrontano sempre il checkout con la loro ultima prova valida, includendo modifiche precedenti mai visitate. Nella CI il runner ricava l'inventario selezionato e assegna circa cento prove per shard, da uno a otto runner, senza partizioni vuote.

`pnpm verify` resta il controllo applicativo completo esplicito, `verify:full` aggiunge tutte le prove browser. I tipi di Cloudflare e React Router si generano con `pnpm typegen` dopo l'installazione e una volta per esecuzione in `verify:tooling`, perché route e configurazione cambiano senza una nuova installazione; `typecheck` e `quality:knip` li leggono senza rigenerarli. Dopo aver aggiunto una route fuori dal gate si esegue `pnpm typegen`; il server di sviluppo li rigenera da sé.

### Qualità del codice e prestazioni

`pnpm quality:knip` blocca il gate per le segnalazioni. Knip ricava gli ingressi dai comandi e dai plugin; `knip.json` aggiunge la configurazione `cf`, il runner mutation e i benchmark. Le primitive in `app/components/ui/` si analizzano come il resto del codice: un componente o un export del kit shadcn senza consumatori va tolto e si rigenera con `shadcn add` quando serve. Gli export usati all'interno dello stesso file non sono considerati inutilizzati. `cloudflare:workers` è un modulo nativo, non una dipendenza npm da installare. Nessuna correzione o cancellazione automatica.

React Doctor (`pnpm doctor:react`, scansione completa bloccante dai warning) gira una sola volta, nel gate completo; il workflow separato che ripeteva la scansione è stato rimosso ([D190](../decisions/DECISION_REGISTER.md)). Oxlint, con il plugin import configurato in `.oxlintrc.json`, rifiuta i cicli fra moduli (`import/no-cycle`, alias `~/` compreso); gli import dinamici restano il modo ammesso per interrompere un ciclo. `pnpm verify:repo` controlla che ogni modulo server abbia un consumatore runtime.

Il gate applicativo esegue `pnpm test:coverage` al posto di `pnpm test`, senza duplicare la suite. Istanbul è compatibile con i progetti Node e Cloudflare. Il report include tutti i file TypeScript/TSX di `app/` e `workers/`, anche se mai importati dai test; esclude solo le dichiarazioni di tipo. HTML, LCOV, JSON dettagliato e riepilogo risiedono in `reports/coverage/`. Il riepilogo verifica conteggi validi e presenza di tutti i sorgenti attesi: un report incompleto fallisce. Righe, rami e funzioni sono segnali diagnostici, senza soglie percentuali. Playwright e i test degli script eseguiti con Node non contribuiscono a queste percentuali. `pnpm test` rimane disponibile per le prove senza strumentazione; mutation e benchmark mantengono la copertura disattivata.

`pnpm benchmark` è un comando manuale, fuori da `verify`, dal classificatore e dalla CI ([D190](../decisions/DECISION_REGISTER.md)). Misura parsing/normalizzazione Fulfillment, qualità formale degli identificativi, conversione importi e generazione in streaming del CSV e dell'XLSX degli ordini per 100, 1.000 e 5.000 ordini sintetici, una riga per articolo con tre articoli e tre identificativi per ordine. Preparazione dati e verifica del contenuto sono esterne alla misura. Tre esecuzioni in sequenza con un solo processo Vitest; `reports/benchmarks/summary.md` riporta mediana e intervallo delle medie. Nessuna chiamata ai provider e nessun confronto automatico con una base: per confrontare due commit si esegue il comando su ciascuno, sulla stessa macchina. Errori, asserzioni fallite o raccolte incomplete fanno fallire il comando. Queste misure non attestano CPU, latenza, memoria o capacità del Worker remoto; per la capacità vale [Capacità e costi](CAPACITY.md#capacita).

Il report di copertura è un artefatto del job che esegue il gate, `Gate` o `Verify`, e della qualifica del candidato, conservato per sette giorni anche in caso di fallimento e non versionato. `Node 26` include Knip e l'integrità della copertura tramite il gate; il riuso dello stesso tree già qualificato conserva le regole di provenienza esistenti.

La selezione mirata riduce le visite del catalogo e le suite funzionali alle aree coinvolte. Una regressione in un'area non selezionata può arrivare su `develop` e sul test: la ferma la qualifica automatica del candidato, prima di `Promuovi` e mai dopo Production ([D253](../decisions/DECISION_REGISTER.md), [D269](../decisions/DECISION_REGISTER.md)). Dopo il deploy test si visitano, con una sola combinazione di layout e tema, soltanto le pagine marcate `remote` nel catalogo (pubblica, accesso, ordini, negozi, profilo e sicurezza del membro, anteprima, 404 e sessione): le altre sono già provate sullo stesso artefatto prima del deploy, mentre il remoto verifica ambiente, D1, sessione e segreti ([D205](../decisions/DECISION_REGISTER.md)). Sul dominio remoto, test e Production, una prova fallita si ripete una volta: se riesce il deploy resta e la ricevuta la conta fra le instabili con un avviso nella run, se fallisce di nuovo il deploy non prosegue.

`Node 26` resta il controllo richiesto e riassume i job `Verify`, che classifica, compila l'artefatto test e ne registra la provenienza, `Gate`, che esegue il gate scelto quando serve la build, e `Browser 1/8`…`8/8`, che dividono le prove browser sull'artefatto caricato da `Verify`. I browser partono appena l'artefatto è pronto, in parallelo al gate, invece di attendere copertura e React Doctor. In una PR non ripartono se l'ultima run della stessa PR che le ha concluse è riuscita in ogni parte, con la stessa impronta dell'inventario selezionato (prove, browser e filtri, salvata nell'artefatto `browser-plan-<run>`), e se fra il suo commit e quello di merge provato ora il classificatore non chiede browser né deploy: un'unione di `develop` con soli documenti, strumenti o test unitari non le ripete ([D318](../decisions/DECISION_REGISTER.md)); senza build il gate resta in `Verify` ([D253](../decisions/DECISION_REGISTER.md)) ([D157](../decisions/DECISION_REGISTER.md), [D205](../decisions/DECISION_REGISTER.md)) e le assegnano a turno nell'ordine dell'elenco di Playwright: `--shard` nativo assegna blocchi consecutivi e concentrerebbe sulla stessa macchina le varianti lente della stessa prova. I job browser della CI e della qualifica del candidato girano nel container ufficiale di Playwright della versione fissata nel manifest ([D190](../decisions/DECISION_REGISTER.md)); [procedura](#installazione-dei-browser). La verifica superata produce `build-<tree>`. Dopo un merge Dependabot, il workflow avvia esplicitamente la CI sul commit integrato, perché gli effetti del token GitHub non generano un nuovo evento push. I deploy sono serializzati; una nuova revisione della PR annulla l'intera run superata, mutation compresa. Con la build, `Verify` esegue subito anche `pnpm verify:documents`: un errore documentale, come una decisione con lo stesso numero di un'altra PR, ferma la run prima che partano browser e mutation. Una PR in bozza esegue soltanto `Verify` e non carica la build per i browser: questi partono quando la PR è segnata come pronta ([D159](../decisions/DECISION_REGISTER.md)).

Il riuso accetta soltanto artefatti non scaduti prodotti da `ci.yml` su `develop` tramite `push` o `workflow_dispatch`, con run riuscita nello stesso repository. Lo SHA della run deve coincidere con quello associato da GitHub all'artefatto e il tree del commit, letto dall'API Git di GitHub, deve coincidere con il tree richiesto. Sono ammessi commit diversi con lo stesso tree, compresi i commit di merge PR già su `develop`. Una build di PR non vale come build di `develop`: una PR interna può modificare il workflow produttore e il suo merge sintetico non è identificato dallo SHA della testa PR. Il push del merge la riusa soltanto con tutte queste condizioni ([D309](../decisions/DECISION_REGISTER.md)): run `pull_request` di `ci.yml` riuscita sull'ultima testa di una PR dello stesso repository integrata in `develop`; artefatto `build-<tree>` del tree integrato, quindi base invariata dopo quella run; commit con un solo genitore, uguale all'ultimo deploy test, così la classificazione del push coincide con quella della PR; nessun file che produce o giudica la prova fra quelli del merge: `.github/`, `scripts/`, manifest, lockfile, workspace, configurazioni `*.config.*`, `tsconfig`, lint, formato, Knip e i file di `e2e/` diversi dalle spec. Allora gate e browser non si ripetono, il deploy distribuisce quella build dopo la verifica del manifest e la run la ripubblica come propria `build-<tree>`, che la qualifica del candidato riconosce come prodotta su `develop`. Altrimenti il merge ripete tutto. Nome e manifest dell'artefatto non costituiscono una prova di provenienza. Anche il riuso di `candidate-<tree>`, nel selettore e nel coordinatore del rilascio, richiede lo stesso legame fra repository, revisione della run e tree, con produttore `candidate.yml` su `develop` tramite `workflow_dispatch` o `schedule` e job «Candidate qualified» riuscito; un errore successivo del deploy non invalida quella qualifica. Il manifest continua a verificare contenuti e configurazione dopo il download.

Il deploy test richiede esplicitamente `Verify` e `Node 26` riusciti e una run non cancellata. Gli skip dei job browser per una build già qualificata non devono propagarsi al deploy tramite il controllo implicito `success()` di GitHub; restano obbligatori evento, branch, abilitazione e classificazione della modifica.

Il livello completo esplicito compila `pnpm build:live` e infine `pnpm build`: entrambi gli ambienti devono funzionare e l'artefatto finale resta quello test. In CI `Verify` produce già la build test: `Gate` esegue `verify:gate` per il livello completo, con strumenti, tipi, copertura, React Doctor e build live, oppure `verify:unit` per il livello build, senza ricompilare il test. Nel candidato il job sorgente compila soltanto il test; il job Production prepara separatamente la build live. La disponibilità dei comandi non autorizza un deploy Production.

### Mutation test

Una PR prova per intero, in modo incrementale, i moduli critici che cambia e quelli importati direttamente da un test che cambia, nei job `Mutation <modulo> <parte>/<parti>` richiesti da `Node 26` ([D301](../decisions/DECISION_REGISTER.md)): un sopravvissuto si corregge nella PR invece di fermare la qualifica, anche quando un test indebolito lo lascia vivo su righe invariate. I moduli raggiunti soltanto attraverso altri import restano al candidato e alla campagna, perché ogni modulo in più costa la prova iniziale della suite che lo copre. Il punto di partenza è il riferimento di `develop`: ogni parte riuscita di una qualifica o di una campagna su `develop` salva il proprio report incrementale nella cache di GitHub Actions, con chiave `mutation-reference-<modulo>-<parte>/<parti>-<run>`, e la PR legge il più recente della stessa parte o, con parti diverse, del modulo. Una parte con superstiti non salva nulla. Dopo le parti, il job `Preserve measured durations` riunisce in un riferimento completo, nella cache `mutation-references-<run>`, ogni modulo con tutte le parti riuscite nella run, e conserva quelli dei moduli assenti o falliti. Con una run precedente della stessa PR, se da allora sono cambiati soltanto file di test e documenti, Stryker parte invece da quella. In entrambi i casi ripete soltanto i mutanti con codice o test cambiati: confronta il testo di ogni mutante e i file di test, ma non vede le altre righe del modulo, i moduli importati né helper e fixture, che restano al candidato. Senza riferimento, per esempio dopo sette giorni senza letture che lo facciano scadere, la PR prova il modulo per intero. Timeout ed errori si provano sempre di nuovo, e una ripetizione dei job falliti parte dai tentativi precedenti della stessa run. La prova iniziale della suite, da cinque a nove minuti sul runner, si ripete in ogni job: un modulo con il riferimento completo e al più 40 mutanti sulle righe cambiate da allora si prova perciò in un solo job, che parte da quel riferimento, invece che nelle parti della campagna ([D315](../decisions/DECISION_REGISTER.md)). La stima conta i mutanti fra la prima e l'ultima riga diversa dal sorgente del riferimento; quelli coperti da test cambiati si ripetono comunque, nello stesso job. Al più sei parti della PR girano insieme. Un modulo già concluso con ogni parte riuscita nell'ultima run della stessa PR che lo ha provato, su un commit antenato del commit di merge provato, non si ripete se da allora non sono cambiati il modulo, i sorgenti che importa anche indirettamente, i test che lo importano direttamente, helper e fixture dei test o migration: un'unione di `develop` che non lo tocca, o una correzione di documenti, non ripete la sua prova ([D317](../decisions/DECISION_REGISTER.md)). Lo stesso criterio vale come prova della PR per il riuso nella qualifica del candidato; il riepilogo della run elenca i moduli riusati con la run che li ha provati. `mutation.yml` gira ogni lunedì alle 03:17 UTC su `develop` e su avvio manuale (`workflow_dispatch`, con moduli facoltativi separati da spazi): un job per modulo critico, al più otto in parallelo e sedici nelle campagne del lunedì notte; le sole campagne scendono a quattro se la pianificazione osserva PR o cicli di pubblicazione attivi o in coda, mentre la qualifica del candidato, automatica o richiesta, scende a sei: il numero si fissa alla pianificazione e vale per tutta la run; nelle PR le parti browser e quelle mutation sono al più quattro ciascuna. Con un tetto per run la coda dei venti posti dell'account resta corta e i job brevi di merge, deploy e pubblicazione partono in pochi minuti, invece di attendere decine di job già in coda ([D321](../decisions/DECISION_REGISTER.md)); il candidato esegue al più quattro parti browser contemporaneamente mentre gira la sua mutation, per lasciare posti ai job di controllo e deploy, e tutte insieme senza mutation, e 60 minuti ciascuno, con la prova iniziale di Stryker entro 20 minuti invece dei 5 predefiniti, che la suite Cloudflare supera sul runner, senza annullare gli altri al primo fallimento. La qualifica del candidato richiama lo stesso workflow per i moduli critici del diff dall'ultimo commit distribuito e i loro consumatori critici. La pianificazione e l'avvio manuale di GitHub leggono il workflow dal branch predefinito, `develop` ([D200](../decisions/DECISION_REGISTER.md)): una modifica di `mutation.yml` vale dalla campagna successiva, senza un'esecuzione al merge.

I moduli critici riguardano Auth, sessioni, isolamento, ordini, export, negozi e integrazioni, oltre a quota e diritti, e sono elencati in `scripts/mutation.mjs`. Anche i moduli condivisi che ne raccolgono le regole, come orari, chiavi derivate, criteri della lista ordini, ritardi della coda e segni dei negozi, sono critici. `pnpm test:scripts` ferma il gate quando un modulo critico importa un modulo non critico assente dall'elenco dei moduli di supporto: una regola estratta in un modulo nuovo resta sotto mutation, oppure la sua esclusione si dichiara nell'elenco. `pnpm test:mutation <file>...` esegue Stryker con runner Vitest sui file indicati, con i test che importano il modulo anche indirettamente o, se nessuno lo importa, con l'intera suite. Ogni mutante deve essere ucciso o avere un'equivalenza motivata con `Stryker disable`; sopravvissuti, timeout ed errori bloccano, nessuna esclusione dei mutanti statici.

Un modulo con più di 150 mutanti si divide in parti di al più 150, una per job e in parallelo: l'instrumenter di Stryker calcola i mutanti e lo script taglia gli intervalli di righe soltanto dove nessun mutante li attraversa, così ogni mutante sta in una sola parte. Se i tagli fra le funzioni lasciano una parte oltre 150, lo script aggiunge una parte, fino a quattro oltre il minimo: con due parti `stores.server.ts` ne aveva una da 162 mutanti che superava i 60 minuti del job; `MUTATION_SHARD=<parte>/<parti>` prova la parte indicata, senza la variabile si prova il modulo intero. La matrice elenca per prime le parti più pesanti, mutanti per file di test che coprono il modulo: i job lunghi occupano subito i posti disponibili, e i brevi riempiono quelli che si liberano. Report e configurazione per modulo o per parte in `reports/mutation/`, conservati come artefatto per sette giorni. La campagna settimanale parte sempre dai sorgenti e rinnova il riferimento di ogni modulo. La prova del candidato è incrementale ([D237](../decisions/DECISION_REGISTER.md)): `scripts/mutation-reuse.mjs` legge le qualifiche e le campagne precedenti su commit antenati e non ripete un modulo critico la cui ultima mutation è riuscita in ogni parte, se da allora non è cambiato nessun sorgente di `app/` o `workers/` che importa, anche indirettamente. Un testo di `app/copy/` cambiato conta soltanto per sé, non per chi lo importa ([D244](../decisions/DECISION_REGISTER.md)). Le qualifiche e le campagne si leggono per workflow, e in una run annullata un modulo interrotto resta senza esito invece di risultare fallito. Se GitHub non restituisce gli esiti precedenti, la pianificazione fallisce e si ripete la run, senza ripiegare sulla mutation completa. Un fallimento recente non si copre con un successo più vecchio. Un modulo critico cambiato, o raggiunto da un altro modulo critico cambiato, non si ripete se ogni suo commit su `develop` viene da una PR dello stesso repository con la mutation del modulo riuscita, sulla testa unita con lo stesso contenuto del modulo nel commit integrato ([D297](../decisions/DECISION_REGISTER.md), [D301](../decisions/DECISION_REGISTER.md)); un sorgente non critico cambiato, o un commit senza quella prova, ripete i moduli che lo importano. Dipendenze, strumenti, configurazioni e prove modificate non fanno ripetere nulla ([D288](../decisions/DECISION_REGISTER.md)): li coprono test, browser e collaudo remoto, e la campagna settimanale, che resta completa.

Le esecuzioni complete riuscite misurano separatamente preparazione e tempo restante della parte. Le misure, conservate nella cache `mutation-timings` soltanto quando le parti complete di una run coprono tutto il modulo, pesano i tagli soltanto sullo stesso contenuto del modulo: il pianificatore bilancia la durata stimata e penalizza le preparazioni ripetute, senza usare tempi incrementali. Senza misure valide vale il numero dei mutanti. La matrice trasmette intervalli e digest ai runner, che verificano copertura completa, contiguità e appartenenza di ogni mutante a una sola parte prima di eseguire Stryker. Le misure decidono la distribuzione, mai quali mutanti provare.

Mutation Auth usa le prove del confine HTTP in Node, con SQLite reale per i limiti dei tentativi e servizi Auth/OAuth sostituiti. Le integrazioni Better Auth, D1, sessioni e provider restano nella suite Cloudflare di `pnpm test`; gli altri moduli conservano il runner Cloudflare.

Il runner mutation esegue i file selezionati in sequenza dentro ogni processo, prima quelli che importano direttamente il modulo: un mutante statico prova tutta la selezione e deve incontrare il test che lo uccide prima del timeout di Stryker. Il runner usa il fallback nativo di Stryker per ricreare l'ambiente quando deve ricaricare un mutante statico. Conserva il limite di quattro processi, ridotto alle CPU disponibili e a un processo per 4 GiB di memoria fisica. Il limite evita che Vitest e workerd provochino attese da paginazione sui computer con poca memoria. La suite Cloudflare concede 15 secondi a ogni test e 20 a ogni hook, anche sotto mutation: con la copertura e più processi sul runner di GitHub, prove che in locale impiegano meno di un secondo superavano i 5 predefiniti e fermavano il gate o il modulo mutation. Il timeout di Stryker per mutante parte da 20 secondi oltre la durata dei test coperti, sopra quello di Vitest: un test bloccato da un mutante fallisce per il proprio timeout e il mutante risulta ucciso, invece di dipendere dal carico della macchina. Timeout, errori e superstiti continuano a bloccare la qualifica; non si ignorano i mutanti statici.

<a id="qualifica-del-candidato"></a>
### Qualifica del candidato

`candidate.yml` qualifica la testa di `develop` da solo ([D269](../decisions/DECISION_REGISTER.md), [D285](../decisions/DECISION_REGISTER.md)). La CI di ogni merge la avvia con un dispatch, perché la pianificazione di GitHub può tardare di ore e resta una riserva oraria; controlla testa, `Node 26` e certificazione. Una qualifica automatica in corso lascia il posto a quella di una testa più recente, che ne contiene i commit, così i merge ravvicinati si accorpano e un commit superato non occupa decine di job ([D321](../decisions/DECISION_REGISTER.md)); le richieste esplicite, come quella di `Promuovi`, e la campagna del lunedì finiscono sempre, e `Promuovi` che seguiva una qualifica automatica annullata ne richiede una esplicita. Le richieste esplicite hanno una coda separata e non sono sostituite dai merge automatici. Le run automatiche dello stesso SHA sono serializzate prima della pianificazione, e così quelle richieste. Qualifica sia cambiamenti distribuibili sia modifiche al processo; una qualifica già attiva sullo stesso commit non si duplica. `release:cycle candidate` la avvia subito sullo SHA esplicito. Il lunedì alle 03:23 UTC una campagna forza tutte le visite, anche sullo stesso tree già certificato. Le pianificazioni GitHub possono partire in ritardo: l'intervallo non è una garanzia di puntualità.

Il workflow riusabile `qualify.yml` esegue gate sorgente, entrambe le build, tutte le prove rimaste dopo il riuso sulla build test in una a otto partizioni, circa cento prove per parte, una visita delle pagine pubbliche sulla build Production locale e la mutation pertinente ([D289](../decisions/DECISION_REGISTER.md)). Le partizioni seguono un'impronta del titolo, non l'ordine dell'elenco. I browser test partono dalla loro build, quelli Production dalla propria senza attendere il job sorgente. La certificazione richiede il successo di entrambi e l'inventario completo, indipendentemente dal numero di parti. Come nelle altre fasi, una prova fallita si ripete una volta; quella riuscita alla ripetizione resta nell'evidenza, e una prova instabile anche in due delle ultime cinque qualifiche ferma la certificazione finché non si corregge ([D271](../decisions/DECISION_REGISTER.md)). Il job `Candidate qualified` controlla provenienza e report delle partizioni: rigenera con Playwright l'inventario completo dei test attesi per ciascun ambiente e richiede gli stessi ID nei report, senza omissioni né prove estranee. Il tree certificato produce `candidate-<tree>`, valido sette giorni. Una ripresa raccoglie l'ultima evidenza per ciascuna partizione senza perdere i job già riusciti.

Le visite di un'area nella qualifica candidata si riusano soltanto con una ricevuta `pages-full` non scaduta, di una qualifica riuscita dello stesso repository su un antenato, per entrambi gli ambienti test e Production ([D272](../decisions/DECISION_REGISTER.md), [D285](../decisions/DECISION_REGISTER.md)). La ricevuta contiene route, file e digest per area: dichiarazioni esplicite e dipendenze transitive delle route si confrontano con il grafo corrente, insieme a configurazioni, dipendenze, migration e strumenti browser. Un digest diverso ripete l'area, un modulo non dichiarato blocca il controllo. Changelog e frammenti invalidano soltanto le aree le cui route consumano `app/whats-new.server.ts`, anche attraverso import transitivi: gli import raw e il glob Vite sono dichiarati nel grafo. Configurazioni, stili, migration e strumenti restano condivisi. Il filtro `--grep-invert` vale anche per l'inventario atteso di entrambi gli ambienti; prove funzionali e nucleo `@remote` restano sempre eseguiti. La build datata dell'effettiva promozione Production mantiene tutte le visite, perché cambia l'input di pubblicazione. L'artefatto dura sette giorni; la campagna settimanale forza il completo e ne rinnova la prova.

La ricerca del candidato ammette soltanto artefatti non scaduti dello stesso tree, dal job di certificazione riuscito del workflow del repository. Una qualifica non distribuisce né autorizza Production.

<a id="versioni-dopo-la-2-0-0"></a>
### Versioni dopo la 2.0.0

Dal tag `v2.0.0` vale [D248](../decisions/DECISION_REGISTER.md). Una funzione entra in `develop` soltanto completa. La prima PR con una Novità per gli utenti dell'app, cioè con voci nelle parti «Novità» e «What's new», dopo l'ultima versione pubblicata aggiunge in cima a `CHANGELOG.md` l'intestazione della successiva, `2.0.x` o `2.y.0`, e le PR seguenti possono alzarne il livello. Le voci di ogni PR stanno nel proprio frammento `changes/<nome>.md`, sotto `## Changelog` con le stesse parti e gli stessi gruppi della sezione, così più PR aperte non si contendono le stesse righe ([D299](../decisions/DECISION_REGISTER.md)); lo stesso frammento porta, sotto `## Decisioni`, le righe delle decisioni nuove con le intestazioni della tabella, e i riferimenti a quelle decisioni puntano già al registro. Build, note di rilascio, catalogo delle prove e controlli leggono il changelog con i frammenti in ordine di nome, che `withChanges` di `app/changelog-fragments.mjs` mette nella versione in cima, dopo le voci già presenti. `release.mjs version-step` rifiuta Novità in un frammento quando la versione in cima è già pubblicata, e una PR può richiudere una versione aperta ancora vuota; al merge il ciclo fa lo stesso confronto sulla base attuale, salvo che la PR apra lei stessa la versione successiva in cima. Se la versione in cima è stata pubblicata mentre la PR aspettava, il ciclo unisce `develop` al branch e apre la patch successiva nello stesso push, così la qualifica parte già sul changelog giusto; con conflitti resta l'aggiornamento di GitHub. Il giorno della pubblicazione riunisce nella versione pubblicata, anche se sopra ne è stata aperta un'altra, e nel registro il contenuto dei frammenti nel commit pubblicato, con i link ricalcolati, e li elimina; righe aggiunte dopo allo stesso frammento e frammenti entrati dopo restano e, se portano Novità, aprono la versione di correzione successiva; dipendenze, prove, refactoring e strumenti non aggiungono voci, e nemmeno un aggiornamento dei soli Termini o Privacy, che ha già la propria notifica ([D264](../decisions/DECISION_REGISTER.md)). `Promuovi` pubblica la sezione in cima con il lotto di `develop`, anche per una correzione urgente. Per una `2.y.0` l'agente prepara prima l'elenco delle prove sul test e `Promuovi` attende l'esito dell'owner ([§34](#s34)). Un lotto senza Novità, con modifiche interne, della console o del sito pubblico, si distribuisce con la versione già pubblicata in cima al changelog, e il giorno aggiunge le sue «Altre modifiche» a quella versione ([D252](../decisions/DECISION_REGISTER.md), [D302](../decisions/DECISION_REGISTER.md)): deploy e collaudo restano completi, il passo del tag conferma il provider e non crea tag né release perché il tag della versione è su un commit precedente dello stesso `main`, e il Worker Production prende l'etichetta `<versione>+<commit>`. Un tag della versione su un commit che non precede il candidato resta un errore.

Le voci per gli utenti (D203) stanno in due parti della sezione, nello stesso ordine: `### Novità` in italiano e `### What's new` in inglese, una voce `- **Titolo.** Testo` per riga sotto i gruppi `#### Funzionalità`, `#### Miglioramenti` e `#### Correzioni` (in inglese `#### Features`, `#### Improvements`, `#### Fixes`), soltanto per nuove funzioni, cambi visibili e correzioni notate dagli utenti nell'area dell'app: i cambi del sito pubblico (pagine, Guide, Prezzi, barra) vanno in `### Altre modifiche`. Il testo parla all'utente in modo chiaro e informativo: dice che cosa cambia per lui, senza dettagli tecnici, spiegazioni difensive di com'era prima o slogan. La pagina mostra i gruppi presenti in quest'ordine. Il resto della sezione, per esempio `### Altre modifiche` con lavoro interno o funzioni della sola console, resta nel changelog e nelle note della GitHub Release, che omettono la parte inglese. La build legge le parti e il test di `test/orders-page.spec.ts` rifiuta voci non corrispondenti o fuori dai gruppi, titoli mancanti, giorni non validi e Novità sulle RC. Una modifica di `CHANGELOG.md` o di un frammento distribuisce dal livello build soltanto se cambia ciò che la pagina Novità mostra, cioè le parti «Novità» e «What's new» e il giorno delle versioni che le hanno; altre modifiche, decisioni e versioni senza Novità restano documentazione, senza deploy test né qualifica ([D303](../decisions/DECISION_REGISTER.md)). Sul test la versione in preparazione compare come «In preparazione» e la campanella la annuncia dal deploy; in Production compare soltanto con il giorno, che la build riceve da `VITE_RELEASE_DAY` ([D273](../decisions/DECISION_REGISTER.md)). Per una `2.y.0` l'agente prepara prima l'elenco delle prove sul test e `Promuovi` attende l'esito dell'owner ([§34](#s34)).

`release.mjs version-step`, nella CI delle PR, controlla la sezione in cima rispetto alla base e ai tag `v2.*`: dopo la `2.0.0` ammette soltanto patch, minor o major successive all'ultima pubblicata, senza scendere di livello. Il Worker del test porta l'etichetta `<versione>-dev.<tree>` e quello Production la versione, uguale all'input del workflow.

<a id="contenuto-delle-pr"></a>
### Contenuto delle PR

Contenuto, impatto sui documenti e collaudo di ogni PR seguono `AGENTS.md`; qui i casi restanti. Fix ordinari, refactoring e miglioramenti dei test si descrivono nella PR, senza una modifica fittizia dei documenti. Le modifiche documentali ordinarie viaggiano con la PR di contenuto successiva; una PR solo documentale serve per decisioni dell'owner, checkpoint o istruzioni da applicare subito. Le ipotesi diagnostiche su CI o test remoto si provano sul branch, con `workflow_dispatch` o con un deploy manuale sul test da worktree pulito seguito dal ripristino della versione attiva, e confluiscono in una sola PR. Modifiche al processo e ai file globali, come manifest, lockfile, workflow e classificatore, viaggiano in una PR alla volta ([D300](../decisions/DECISION_REGISTER.md)): ognuna rende incompatibili le PR aperte e chiede una nuova qualifica. Mentre una qualifica è in corso non si aprono altre PR sul processo, salvo la correzione del difetto che la blocca. Dependabot apre i suoi aggiornamenti il lunedì mattina, fuori dagli orari di lavoro. Il readback del deploy test conferma la PR integrata e si riferisce all'owner; un esito negativo apre la PR di correzione, che registra il difetto. Le pendenze ancora utili alla ripresa restano nelle [questioni aperte](../ROADMAP.md#questioni-aperte).

<a id="ciclo-operativo"></a>
### Ciclo operativo

Il comando si esegue soltanto nel mandato corrispondente: `Pubblica` usa `pr`, `Promuovi` usa `promote`. `status`, `metrics` e `preflight` sono in lettura; gli altri comandi possono modificare PR, Git o avviare workflow. Richiedono un checkout pulito, salvo quando il ciclo gira in Actions. I cicli su oggetti diversi (due PR, una PR e una ripresa) procedono insieme e ne resta uno solo per oggetto.

```sh
pnpm release:cycle status <run>
pnpm release:cycle metrics
pnpm release:cycle pr <numero>
pnpm release:cycle production <numero>
pnpm release:cycle cleanup
pnpm release:cycle candidate
pnpm release:cycle promote [--version <versione>] [--urgente] [--testa]
pnpm release:cycle resume <run>
pnpm release:cycle rollback
```

`pr`, `production`, `promote`, `rollback` e `resume` girano in `cycle.yml` quando `publication` ha il segreto `PUBLISH_TOKEN` ([D274](../decisions/DECISION_REGISTER.md), [D285](../decisions/DECISION_REGISTER.md)). Input e titolo legano operazione, oggetto e SHA atteso; `promote` pubblica soltanto quello SHA, che `develop` deve contenere, e i merge successivi aspettano il lotto seguente. Ogni PR ha il proprio gruppo, `publication-cycle-pr-<numero>`, così più `Pubblica` procedono insieme e nessuna sostituisce un'altra in coda ([D295](../decisions/DECISION_REGISTER.md)); `publication-cycle-release` serializza `promote` e le riprese di `publish.yml`, compreso l'avanzamento di `main`, e le PR raggiungono il test anche con una promozione in corso ([D286](../decisions/DECISION_REGISTER.md)). La ripresa di una run della CI o di una qualifica ha il gruppo `publication-cycle-run-<run>` e non aspetta una promozione; il ritiro ha un gruppo proprio e non aspetta un ciclo in corso; le qualifiche CI delle PR restano parallele. `production` esegue il ciclo della PR nel suo gruppo e poi, in un job del gruppo delle promozioni, `promote` sul commit certificato più recente che contiene il commit integrato della PR, o sulla testa se nessuno lo è: un merge successivo può aver annullato la CI di quel commit. I coordinatori girano sulla testa di `develop` e nessuno attende i controlli di un altro. Il comando avvia e segue la run: chiudere la sessione non la ferma. Un coordinatore passa quasi tutto il tempo ad aspettare altre run, quindi il comando lo manda sui runner `fiscalbay-coordinator` del Mac dell'owner quando uno è acceso e libero, e sulle Actions altrimenti: l'attesa non toglie posti ai venti job contemporanei dell'account ([D321](../decisions/DECISION_REGISTER.md)). Se il Mac si spegne durante un ciclo, la run fallisce e lo stesso comando la riprende. Sul Mac il coordinatore esegue soltanto codice di `develop`, senza installare dipendenze né toccare la configurazione Git globale; `verify:repo` rifiuta il runner in ogni altro workflow e le PR da fork attendono sempre l'approvazione dell'owner prima di eseguire workflow. `promote` su un tree già certificato non attende gli altri controlli del commit: basta `Node 26` riuscito. GitHub conserva un solo ciclo in coda per gruppo, e uno sostituito si rilancia. Il ciclo non manda avvisi Telegram ([D288](../decisions/DECISION_REGISTER.md)). `--qui` consente la sola PR iniziale che introduce il workflow, nella sessione; le operazioni Production usano il coordinatore configurato. I blocchi Git locali proteggono soltanto il clone, non fungono da lock fra runner.

`pr` gestisce una PR dello stesso repository verso `develop` ([D184](../decisions/DECISION_REGISTER.md)). Qualifiche e attese delle PR procedono in parallelo; il merge è l'unico passo in fila, sotto un blocco fra runner e sessioni: il riferimento `refs/locks/merge`, che GitHub crea una sola volta e rifiuta con 422 a chi arriva dopo. Il suo commit, sul tree di `develop`, porta titolare e ora; il titolare lo rimuove soltanto se è ancora il suo, con un push con lease sullo SHA letto che il server applica in modo atomico, e un blocco più vecchio di 60 minuti, lasciato da un ciclo interrotto, si rimuove allo stesso modo. Sotto il blocco il ciclo attende i controlli al più 15 minuti e il merge al più 30 ([D295](../decisions/DECISION_REGISTER.md)). Sotto il blocco il ciclo rilegge la base, rifiuta voci di frammenti se la versione in cima della base ha già tag o giorno, e, se un'altra PR ha già portato su `develop` il numero di una decisione nuova, lo sposta dopo l'ultima nelle righe Markdown aggiunte dalla PR, con un commit sul suo branch, e la riqualifica; una riga esistente modificata dalla PR, come «Superato da», non è una decisione nuova ([D299](../decisions/DECISION_REGISTER.md)). Sospende il merge automatico, si ferma subito se la PR aggiunge migration non additive senza la riga di approvazione e, quando la riga arriva dopo un `Verify` fallito per questo motivo, ripete i soli job falliti. Aggiorna la base mediante merge soltanto se i commit entrati nella base dal punto di divergenza non sono compatibili con la testa e segue la run più recente non annullata sulla testa, anche se già in corso, senza rimettere la PR in bozza; una PR in bozza viene segnata come pronta. Una base è compatibile se i file cambiati dalla PR e quelli entrati nella base sono disgiunti, esclusi changelog e documenti di `docs/` che quasi ogni PR tocca ([D275](../decisions/DECISION_REGISTER.md)), nessuna delle due parti tocca file globali (manifest, lockfile, `tsconfig`, configurazioni `*.config.ts`, workflow, classificatore, script di pubblicazione, strumenti di `e2e/`) e le migration nuove arrivano da una parte sola ([D195](../decisions/DECISION_REGISTER.md)).

Se la qualifica fallisce mentre la base è avanzata in modo non compatibile, il ciclo aggiorna di nuovo la PR e segue la nuova run, al massimo tre volte; altrimenti un fallimento ferma il ciclo. La CI rifiuta una base non compatibile prima dei job costosi; il controllo finale avviene al merge, dove il ciclo rilegge la base sotto il blocco, senza far fallire una run già conclusa. Dopo la qualifica riuscita il ciclo attiva automerge sulla stessa testa e segue il commit integrato. Una PR integrata senza aggiornamento produce un tree nuovo: il push su `develop` non riusa l'artefatto della PR, riesegue gate e browser sul tree integrato e distribuisce soltanto se riescono.

Il deploy test usa una coda con un solo posto ([D276](../decisions/DECISION_REGISTER.md)). Un job che trova `develop` avanzato lascia il deploy alla run del nuovo commit e riesce senza distribuire; il confronto seguente parte dall'ultimo deploy effettivo. Un merge durante il deploy non invalida la conferma di un antenato. Il ciclo segue i discendenti fino a una scadenza complessiva di un'ora, senza un limite al numero di merge, e richiede deploy e readback quando necessari. Un guasto si riprende sulla run originale, senza avviarne una equivalente. `Confirm provider readback` verifica ricevuta, report remoti e versione attiva con i segreti del workflow. Un deploy non richiesto non viene inventato. Una PR integrata si riconcilia senza un nuovo merge; il ciclo pulisce il proprio branch e ogni `promote`, anche senza deploy, esegue la pulizia dei residui integrati.

`promote` pubblica lo SHA atteso di `develop`, secondo [Promuovi e ripresa](#promuovi-e-ripresa); `candidate` lo certifica senza effetti su `main`. `rollback` ritira la versione attiva. `resume` conserva input e ricevute e ripete soltanto i job falliti: una ricevuta ritirata resta tale e non può diventare verde osservando la vecchia versione sana, e il comando lo verifica sull'ultima ricevuta della run prima di ripetere i job. Dopo un deploy test serve `Confirm provider readback`; in Production servono anche giorno, `Conferma pubblicazione attiva`, tag/release e un nuovo confronto fra dominio e ricevuta.

Il client registra le PR seguite nella cartella Git del proprio worktree. Dopo il successo remoto riconcilia PR, SHA e contenuto prima di pulire i riferimenti locali. Alla successiva operazione riprende le pulizie pendenti: modifiche locali o worktree in uso restano conservati e dichiarati, senza presumere che il runner abbia pulito il Mac.

Le letture GitHub con 502, 503, 504 o errori transitori di connessione si ripetono fino a quattro volte con attesa crescente. Merge, push e dispatch con risposta incerta non si duplicano: si riconciliano con PR e run già esistenti. Dopo una risposta 5xx all'attivazione del merge automatico il ciclo rilegge la PR: se il merge automatico è attivo o la PR è unita l'effetto è arrivato, altrimenti ripete la richiesta, al più quattro volte; il 2026-11-04 un 502 su #646 aveva fermato il coordinatore. Un errore nel rilevare il coordinatore non abilita una promozione locale priva della serializzazione remota.

La pulizia confronta gli SHA e ricostruisce con `git merge-tree` il tree completo atteso della PR squash: differenze anche di soli spazi, conflitti o nuovi commit impediscono l'eliminazione. Usa una lease sul branch remoto e preserva i riferimenti protetti. Riallinea la base con fast-forward; se la base è già attiva in un altro worktree, come accade lanciando il ciclo da un worktree dedicato, stacca il checkout corrente sulla base remota. `cleanup` e `promote` esaminano anche branch temporanei precedenti. Conserva lavoro diverso o branch usati da altri worktree e dichiara i residui. Stash e worktree non creati dal comando restano nell'inventario: il comando non ne presume ownership né assenza di processi o dati ignorati da conservare.

Le sessioni Claude Code cloud eseguono gli stessi comandi; dal browser e dall'app partono dal branch predefinito, `develop` ([D200](../decisions/DECISION_REGISTER.md)). All'apertura della sessione `.claude/settings.json` avvia `.claude/hooks/cloud-session.sh`, che riusa Node e pnpm del manifest se l'ambiente li fornisce già, per esempio con mise nel suo script di setup, altrimenti li installa verificandoli con i checksum ufficiali; poi installa le dipendenze del lockfile; in locale non fa nulla. Lo stesso file ammette senza conferma, anche sul Mac, le letture Git e GitHub, i gate locali `pnpm verify:*` e `pnpm test:*` e `pnpm release:cycle status`; push, merge e deploy restano soggetti alle conferme del client.

Nei thread dei progetti Claude gli hook del repository non partono: lo script di setup dell'ambiente cloud, che parte dalla cartella sopra il clone ed è comune a più progetti, aggiunge `if [ -d FiscalBay ]; then (cd FiscalBay && CLAUDE_CODE_REMOTE=true bash .claude/hooks/cloud-session.sh); fi`, così le dipendenze sono pronte all'apertura del thread. Senza quella riga si lancia a mano lo stesso script e, se ha scaricato Node, si antepone ai comandi la riga `PATH` che stampa.

Il proxy GitHub delle sessioni rifiuta GraphQL: il ciclo usa l'API REST e, con `CLAUDE_CODE_REMOTE=true`, le route del proxy per merge automatico e uscita dalla bozza; il branch della PR lo elimina GitHub dopo il merge. La sessione non ha credenziali Cloudflare: deploy, collaudo remoto e readback restano nei workflow, qualunque sia la rete dell'ambiente. Le prove browser locali usano i browser che l'ambiente fornisce, per esempio con `PLAYWRIGHT_BROWSERS_PATH`; senza, restano alla CI.

`status` calcola l'unione degli intervalli dei job di tutti i tentativi: tempo attivo e tempo senza job, comprese attese e pause prima della ripresa. I job paralleli non si sommano e un secondo tentativo non viene confuso con una singola esecuzione lenta. `metrics` riporta durata e tentativi delle ultime pubblicazioni, con la mediana e quante sono riuscite al primo tentativo, e per le ultime qualifiche del candidato l'attesa in coda, la durata di browser e mutation e i minuti di runner. I motivi del mancato riuso compaiono nei riepiloghi delle run. Non si crea un secondo diario o stato di pubblicazione.

Le metriche delle ricevute separano richiesta, certificazione, attivazione e completamento; riportano attesa dei runner su tutti i tentativi, ritiri e contraddizioni fra verde e versione osservata ([D285](../decisions/DECISION_REGISTER.md), [D288](../decisions/DECISION_REGISTER.md)). `successfulRuns` e `medianRunMinutes` descrivono le run GitHub; `published` conta soltanto pubblicazioni con ricevuta confermata. I tentativi comprendono nuove run sullo stesso SHA, non soltanto `run_attempt`. Un candidato corretto con SHA diverso resta distinto; un dato assente è `null` o evidenza assente. Il completamento misura il tempo dall'attivazione alla conferma finale.

## Tutte le pagine

`e2e/page-cases.ts` dichiara route, parametri e ruoli. `pnpm verify:pages` confronta il catalogo con `app/routes.ts`: aggiungere una route senza scenario blocca il gate. I dati dei parametri dinamici e gli stati significativi si aggiungono nel catalogo; non si deducono tutti i possibili ordini o utenti da un crawler.

Il controllo verifica anche che tutte le sezioni dichiarate delle Impostazioni abbiano un caso in italiano e inglese, e segnala gli scenari rimasti dopo la rimozione di una route.

`pnpm test:pages` visita ogni scenario in italiano e inglese, a 390, 768 e 1280 px, nei due temi, con Chromium e WebKit. Controlla risposta, redirect, lingua, titolo, contenuto, ricarica, navigazione, errori JavaScript e risorse, immagini, collegamenti, overflow, tastiera e WCAG A/AA con axe. In ogni esecuzione, anche nelle PR, la prima combinazione di ogni scenario misura lo scorrimento orizzontale ai bordi dei breakpoint, da 320 a 1280 px, ridimensionando la pagina già aperta e con i pannelli richiudibili aperti. `pnpm test:e2e` esegue entrambi i browser anche per le prove funzionali; `pnpm verify:full` aggiunge la matrice completa delle sei combinazioni di larghezza e tema. Il manifest iniziale contiene tutte le route, senza richieste di scoperta concorrenti alla navigazione. Nessun confronto automatico degli screenshot.

Le prove attendono la rete ferma con `networkIdle` di `e2e/fixtures.ts`, mai con `waitForLoadState("networkidle")`. Playwright ritira quell'evento a `load` quando è scattato prima e nel frattempo sono partite richieste, senza riarmarlo. Sui runner WebKit lenti accade perché `entry.client` importa i testi della lingua prima dell'idratazione, e l'attesa resta bloccata fino al timeout. Un contesto creato nella prova si osserva con `watchNetwork` prima di aprirne le pagine. Né la rete ferma né un controllo visibile provano l'hydration: dopo una `reload`, un clic che richiede React passa da `clickHydrated` di `e2e/components.ts`, che attende l'elemento collegato.

Le prove che modificano dati locali usano account distinti per browser e flusso. Questo non sostituisce la verifica passkey su Safari/iOS reale.

Il database locale contiene utente, amministratore e sessioni sintetiche: non esiste un bypass runtime. Il collaudo Production locale usa la D1 Production della build live, con le sole migration applicate prima dell'avvio della preview e senza account. Il preview riceve soltanto segreti sintetici, rimossi dall'artefatto prima dell'upload. Il membro verifica sia il dato sbloccato sia l'assenza del dato bloccato dall'HTML. Sul test remoto si usa soltanto l'account di collaudo `collaudo@example.invalid`: `pnpm test:e2e:smoke`, il controllo breve dopo il deploy senza server locale, entra nell'area riservata con `E2E_ACCOUNT_PASSWORD`, segreto dell'environment GitHub `test`, dopo che `node scripts/reset-test-account.mjs` ha riportato l'account a uno stato noto sulla sola D1 `fiscalbay-test`; se il ripristino fallisce le prove autenticate si saltano con un avviso, senza rollback. Amministratore e MFA non vengono sintetizzati sul provider. Un account remoto indisponibile produce esplicitamente un collaudo parziale. Production esegue soltanto visite anonime e verifica che l'anteprima risponda 404.

In Production l'anteprima assente viene verificata una volta per ciascun pattern di route, in entrambe le lingue e nella matrice dei browser/temi/viewport. Non si ripete lo stesso 404 per ogni identificativo sintetico o sezione della simulazione. La build test mantiene tutti gli scenari.

Il reporter scrive `test-results/browser/summary.json` e il riepilogo GitHub con pagine, browser, esiti e motivi delle esclusioni. Le tracce restano disponibili soltanto in locale; il report remoto non contiene DOM, cookie o dati degli account. Le sentinelle invisibili di Base UI per il cursore VoiceOver in WebKit sono escluse soltanto dalla regola `aria-command-name`: non sono comandi utente. Ogni altro nodo e regola resta controllato. Axe e WebKit non attestano un dispositivo Safari/iOS né i flussi esterni fiscali o di pagamento.

Ogni visita registra route, risposta/percorso attesi, controlli effettivamente completati e omissioni. I collegamenti interni devono risolvere un pattern registrato; la navigazione verifica anche Avanti quando applicabile. Il report identifica commit, ambiente e sorgenti modificati: la release rifiuta un report vuoto, parziale, di un checkout non salvato, di un altro candidato o del dominio test.

Le prove locali usano due worker, quattro per ciascuna macchina in CI, quelle remote uno. Ogni caso ha un limite di 60 secondi per visita, audit, ricarica e navigazione; non è una soglia di velocità della pagina. La durata effettiva di ciascun caso entra nel report JSON. In CI e nella qualifica ogni prova fallita si ripete una volta, come sul dominio remoto: se riesce resta nel report e nella run come instabile, se fallisce di nuovo blocca il gate.

## Artefatto e readback

`node scripts/release/release.mjs manifest --environment test` registra commit, tree, SHA256 dell'artefatto, configurazione, lockfile, toolchain e hash delle migration. `verify` controlla gli stessi input prima della distribuzione. Un merge può cambiare commit conservando il tree. Il deploy rifiuta un candidato superato sul branch remoto, che in Production è un commit diverso dalla testa di `main`, e registra l'identità completa nelle annotazioni della versione Cloudflare.

Il Worker restituisce `x-fiscalbay-version` dal binding nativo di Cloudflare. Il readback confronta questa versione su `/`, `/en` e `/api/auth/get-session` e, poiché l'edge può servire la versione precedente per qualche secondo dopo il deploy, riprova per circa un minuto prima di fallire. La ricevuta `reports/release.json` distingue schema applicato, deploy e readback. D1 espone i nomi delle migration applicate: gli hash SQL nella provenienza sono locali, non un attestato byte per byte del remoto.

Quando la precedente versione espone un commit qualificato, le migration già applicate devono coincidere byte per byte con quel sorgente Git. Una migration applicata che quella versione non contiene, perché un candidato successivo l'ha applicata ed è stato ritirato, vale soltanto se fra la versione attiva e il nuovo candidato il file è stato aggiunto una volta e mai modificato. Una versione storica senza identità qualificata non permette questo confronto: il primo ciclo test deve registrare tale limite. La provenienza rifiuta un checkout con modifiche non salvate nel commit.

Le migration nuove additive (tabelle, indici, colonne aggiunte, azioni referenziali delle chiavi esterne) vengono applicate prima del deploy, poi rilette dal registro D1. Quelle con `DROP`, `RENAME`, altre `ALTER`, trigger o scritture sui dati esistenti (`INSERT`, `UPDATE`, `DELETE`, `REPLACE`) richiedono il digest esatto del piano nel campo `reviewed_migrations`. Il primo tentativo senza digest mostra il valore da esaminare e si arresta prima dell'applicazione. Una PR verso `develop` che aggiunge migration di questo tipo si ferma in `Verify` finché il corpo non contiene la riga `reviewed-migrations: <digest>` stampata dal controllo, dopo l'esame; `node scripts/release/release.mjs review --base <sha-base>` lo calcola in locale. Il deploy test dopo il merge usa quel digest se il dispatch non ne indica uno: coincide quando il test distribuisce già la base della PR, altrimenti il deploy si arresta come prima. Production non chiede una seconda approvazione ([D277](../decisions/DECISION_REGISTER.md)): il preflight rilegge le PR del lotto, ricalcola il digest di ciascuna dal suo commit e ne ricava quello del lotto; `--reviewed-migrations` serve soltanto se una PR non ha la riga. Non riutilizzare il digest dopo modifiche al piano. I file delle migration già applicate restano immutabili.

Prima della migration si ricontrolla il candidato remoto; un artefatto diverso dello stesso commit viene rifiutato prima degli effetti. Il piano approvato è salvato nella ricevuta: una ripresa può completarne il sottoinsieme ancora pendente, soltanto con gli stessi hash SQL e lo stesso digest approvato. Un cambiamento della versione provider durante il preflight impedisce il deploy. Una risposta CLI persa dopo un deploy viene riconciliata con l'identità provider, così il rollback può usare un esito effettivamente confermato.

Il rollback automatico è ammesso soltanto senza nuove migration e con precedente versione identificata, configurazione e migration uguali. Altrimenti resta necessario un forward-fix o una compatibilità qualificata. Prima del rollback si rilegge la versione attuale: uno stato cambiato impedisce di sovrascrivere un altro deploy. Il rollback del codice non ripristina dati.

La versione nuova si prova prima di ricevere traffico ([D278](../decisions/DECISION_REGISTER.md)), sul test a ogni deploy e in Production. Dopo le migration `deploy` la carica con `cf workers versions create --prebuilt` e crea un deployment con la nuova al 0% e la precedente al 100%; `staged-check` conferma che l'header `Cloudflare-Workers-Version-Overrides` raggiunge la versione, perché Cloudflare ignora un override non valido, e le visite vanno sul dominio reale con quell'header (`E2E_VERSION_OVERRIDE`). `activate` porta la versione al 100%, se nel frattempo la versione attiva non è cambiata, e rilegge. Se il collaudo fallisce la versione esce dal deployment senza aver visto traffico. Le migration sono già applicate: le additive restano compatibili con il codice precedente, le altre richiedono la correzione in avanti. Una configurazione diversa si applica a route e cron soltanto con `cf deploy`: in quel caso il traffico passa subito e il collaudo segue, con il rollback della procedura precedente.

L'override vale sia per navigazioni browser sia per richieste API; `E2E_EXPECTED_VERSION` fa verificare l'identità di ogni risposta del catalogo. Una risposta persa dopo upload o attivazione si riconcilia con l'identità provider prima di ripetere l'effetto. Il ritiro già completato è idempotente; una terza versione estranea resta un errore. I test degli script eseguono gli entrypoint reali con CLI e rete simulate, includendo risposte perse, conferma senza attesa, ritiro, ripresa e giorno fallito.

### Qualifica sul provider test

Le migration della CLI si provano su una D1 temporanea in UE, senza binding del Worker e senza dati dell'app. Si usano copie delle migration reali: un errore SQL deliberato in una copia deve fermare l'applicazione, lasciare registrate solo le migration precedenti e annullare le modifiche della migration fallita. Ripristinare la copia originale, ripetere `cf d1 migrations apply <id> --dir <cartella>` e confrontare il registro con i file; un'ulteriore ripetizione non deve applicare nulla. Eliminare la D1 temporanea e verificarne l'assenza. Questa prova qualifica il percorso CLI e la transazione, senza sostituire il collaudo di una futura migration sui dati applicativi o il recovery dei dati.

Per la ripresa del deploy recuperare l'artefatto originale della CI su un checkout pulito dello stesso tree, poi eseguire `node scripts/release/release.mjs deploy --environment test`, prima senza ricevuta locale e poi con quella confermata. Identità, versione e deployment ID del provider devono restare invariati: lo script riconcilia il deploy esistente e salva il readback. La prova senza ricevuta non ricostruisce una versione precedente né autorizza automaticamente il rollback. La ripetizione del job `Deploy test` della stessa run copre anche il recupero della ricevuta conservata da GitHub e ripete il collaudo autenticato.

Il rollback usa una ricevuta confermata con `rollbackCompatible: true` e deve terminare col readback della versione precedente. Prima della prova controllare anche che le risorse dei binding non siano state eliminate o ricreate dopo quella versione, in particolare le Queue: uguaglianza della configurazione Git e nomi uguali non rendono di nuovo distribuibili le vecchie versioni. Ripristinare quindi il candidato corrente tramite `deploy` con lo stesso artefatto originale, conservare la nuova ricevuta e ripetere il collaudo remoto. Rileggere branch e provider prima di ogni effetto; un avanzamento concorrente richiede riconciliazione, senza sovrascriverlo con il candidato della prova.

## Promuovi e ripresa

`release:cycle promote` sceglie il commit più recente di `develop` dopo `main` con il tree già certificato, e con la versione richiesta in cima al changelog se `--version` la indica: i merge successivi passano al lotto seguente, e il comando dice quanti sono ([D296](../decisions/DECISION_REGISTER.md)). Senza un commit certificato, o con `--testa`, vale la testa, di cui si attende la qualifica. Fissato lo SHA, esegue il preflight prima di attendere CI o candidato: versione realmente attiva, superficie da distribuire e approvazioni delle migration ([D273](../decisions/DECISION_REGISTER.md), [D285](../decisions/DECISION_REGISTER.md)). `find-deployed.mjs` legge la versione dal dominio e cerca la ricevuta corrispondente, anche in run fallite o dopo un ritiro: il colore della run non è lo stato Production. Le ricevute anteriori restano leggibili soltanto con versione e readback coerenti. Un segreto aggiornato con la CLI crea una versione con lo stesso codice ma senza ricevuta: per la sola base del lotto vale allora l'ultimo stato registrato da pubblicazione o ritiro, con un avviso, mentre la conferma finale richiede la ricevuta della versione servita. Uno stato più recente ritirato o illeggibile non fa ripiegare su uno più vecchio. Senza deploy `main` avanza e il ciclo riconcilia e pulisce; aspetta prima il candidato soltanto se il lotto cambia la procedura che gira da `main`: `publish.yml`, `rollback.yml`, `qualify.yml`, `mutation.yml`, le Action, gli script e le prove browser. Documenti, test e workflow della CI di `develop` non lo richiedono. Con un deploy servono `Node 26` e certificazione del tree, poi il coordinatore avanza `main` e avvia `publish.yml`.

`publish.yml` gira su `main` perché l'environment `production` lo richiede. `Verifica candidato` ripete il preflight e rifiuta un tree senza certificazione. `Qualifica Production` prepara con `pnpm build:live` la build con il giorno della versione, l'unica che si distribuisce: il tree è già certificato e cambia soltanto il giorno, quindi le prove sono quelle sul dominio reale. `Distribuisci e verifica` applica le migration, carica la versione senza traffico, visita ogni pagina pubblica una volta in Chromium e WebKit sul dominio reale ([D258](../decisions/DECISION_REGISTER.md)), attiva e rilegge; poi crea tag e GitHub Release dalle note della versione. Un tag già esistente deve puntare al commit atteso, senza riscritture. `PRODUCTION_PUBLISH_ENABLED` e l'environment Production limitato a `main` ([D250](../decisions/DECISION_REGISTER.md)) restano l'interruttore del rilascio: dopo il go-live i gate del piano non si rileggono più a ogni promozione ([D284](../decisions/DECISION_REGISTER.md)).

Non è prevista una guardia a tempo dopo il deploy ([D288](../decisions/DECISION_REGISTER.md)). Dopo `publish`, `Giorno della versione` scrive il giorno su `develop`, poi `Conferma pubblicazione attiva` rilegge il provider e richiede il candidato atteso. La ricevuta registra anche la versione tornata attiva dopo un ritiro; una ripresa rifiuta il candidato ritirato. `production-state-<versione-provider>` conserva per 90 giorni SHA, identità/digest, schema osservato, tempi di attivazione, completamento e ritiro. L'annuncio finale segue questa riconciliazione; il giorno da solo non provoca un deploy.

Con `--urgente` si usano soltanto prove già valide sul tree, senza attese per produrle né bypass della certificazione ([D283](../decisions/DECISION_REGISTER.md), [D285](../decisions/DECISION_REGISTER.md)). Restano build Production, prova prima del traffico e readback finale. Senza certificazione il comando si ferma prima di avanzare `main`; per contenere un incidente restano l'interruttore della funzione e il rollback compatibile.

`release:cycle rollback` avvia `rollback.yml` ([D283](../decisions/DECISION_REGISTER.md)), che riporta al 100% la versione precedente senza artefatti né ricostruzioni: è ammesso soltanto con configurazione e migration uguali fra le due versioni, altrimenti serve la correzione in avanti. Una run di rollback riuscita ritira dal confronto la pubblicazione precedente: la promozione successiva ridistribuisce il lotto.

Una ripresa rilegge registro D1, branch e identità provider; le migration già applicate e il deploy già confermato non si ripetono. La creazione della release può ripartire dopo un tag riuscito. Nei tentativi successivi della stessa run i workflow recuperano la ricevuta del tentativo precedente non scaduto, verificandone candidato, artefatto e ambiente prima di usarla. Una nuova run senza tale riferimento non inventa una versione precedente.

Subito prima del tag, `confirm` rilegge branch, versione provider e risposte HTTP, senza applicare migration o ridistribuire. Un cambiamento rispetto alla versione collaudata blocca la release. Sul test lo stesso `confirm` chiude il job `Deploy test` e richiede anche i report `test-smoke` e `test-pages` completi dello stesso commit; un esito negativo fa fallire la run senza tornare indietro.

Dopo un fallimento del collaudo o del tag, usare la ripetizione dei soli job falliti su GitHub per conservare l'artefatto originale qualificato. Una ricostruzione dello stesso commit con digest diverso viene rifiutata se quel commit è già distribuito: non viene scambiata per una ripresa della stessa versione.

Qualifiche remote mancanti, recovery, restore dei dati e prova merchant sono nelle [questioni aperte](../ROADMAP.md#questioni-aperte). I dettagli delle esecuzioni restano in PR/CI e ricevute, senza diario nel piano. Le PR dichiarano l'impatto sul piano; requisiti, checkpoint, avanzamento significativo e pendenze si aggiornano nella stessa PR dell'implementazione, prima del merge.

## 34. Git, CI/CD, versioning, Pubblica e Promuovi

Branch feature→`develop`, integrato su `test.fiscalbay.it`; `main` è la testa di `develop` promossa e avanza soltanto in fast-forward ([D273](../decisions/DECISION_REGISTER.md)). Nessun deploy live automatico. Autodeploy test dopo merge su `develop` con gate e separazione dati; le migrazioni pericolose non diventano innocue per il solo ambiente test. La 1.x congelata resta soltanto nella storia Git, raggiungibile da `v2.0.0`; nessun merge su `develop` può avviare il deploy 1.x.

**Invarianti della pipeline.** Qui restano le regole che cambiano soltanto con una decisione; funzionamento, comandi e criteri tecnici vivono nella [procedura di pubblicazione]() e nel codice.

- Action di terze parti pinnate allo SHA completo con la versione in commento, aggiornate da Dependabot; permessi minimi; PR da fork senza segreti né scritture live. CodeQL, dependency review, secret scanning e controlli licenze dove disponibili, senza presumere capacità o costi GitHub senza preflight.
- `develop` richiede `Node 26`, riepilogo di gate, build e browser, con i browser in parallelo al gate sull'artefatto già compilato ([D157](../decisions/DECISION_REGISTER.md), [D190](../decisions/DECISION_REGISTER.md), [D253](../decisions/DECISION_REGISTER.md)), e ammette il merge automatico soltanto con controlli verdi; l'amministratore conserva la possibilità di intervenire. `main` riceve soltanto commit di `develop` con `Node 26` verde, senza PR, e la build riceve il giorno della versione, che `develop` scrive dopo la pubblicazione ([D273](../decisions/DECISION_REGISTER.md)).
- Un classificatore unico per locale e CI sceglie fra cinque livelli (documenti, strumenti, test applicativi, build, completo), le prove browser e il deploy secondo l'impatto ([D162](../decisions/DECISION_REGISTER.md), [D190](../decisions/DECISION_REGISTER.md), [D192](../decisions/DECISION_REGISTER.md), [D195](../decisions/DECISION_REGISTER.md), [D253](../decisions/DECISION_REGISTER.md)); ogni modulo applicativo dichiara un'area, nessuna pagina o la suite completa, e un modulo senza dichiarazione ferma il gate ([D265](../decisions/DECISION_REGISTER.md)); le prove browser delle PR seguono quella dichiarazione, con WebKit quando cambia ciò che il browser esegue e le dipendenze per tipo ([D266](../decisions/DECISION_REGISTER.md), [D267](../decisions/DECISION_REGISTER.md)); in locale prova soltanto le modifiche successive all'ultimo verde, con i controlli statici del livello e i test collegati al diff, senza browser salvo `pnpm verify:browser`, che li apre soltanto se cambia ciò che il browser esegue ([D268](../decisions/DECISION_REGISTER.md), [D298](../decisions/DECISION_REGISTER.md)); ogni livello esegue uno script di `package.json`, unica definizione della sequenza, e comprende il precedente. I soli valori testuali delle variabili del Worker test distribuiscono dal livello build, senza prove browser della PR; ogni altra modifica di `cloudflare.config.ts` resta completa. File non classificati o confronti non disponibili eseguono il gate completo e il riepilogo CI ne espone i motivi. Il gate completo comprende install con lockfile congelato, formato, lint, typecheck, React Doctor, test e build; i browser seguono l'impatto e girano nell'immagine ufficiale di Playwright della versione del manifest. Un diff solo documentale non ridistribuisce.
- Il riuso di build e prove richiede lo stesso tree o gli stessi input, da run riuscite del repository, senza origine fork né artefatti scaduti. Il deploy test distribuisce l'artefatto verificato senza ricompilarlo.
- Mutation sui domini critici (sblocco, quota e grant, diritti Stripe, ingresso webhook, Auth, ordini, negozi, export), con il perimetro dei file nel repository: le PR provano in modo incrementale i moduli critici cambiati o importati da un test cambiato, dal riferimento di `develop` ([D301](../decisions/DECISION_REGISTER.md)), il candidato i moduli critici modificati e i loro consumatori critici, salvo quelli già provati nella PR sullo stesso contenuto, senza ripetere tutti i moduli quando cambiano la pubblicazione, il classificatore, le prove browser o gli strumenti della mutation ([D317](../decisions/DECISION_REGISTER.md)), la campagna settimanale tutti ([D173](../decisions/DECISION_REGISTER.md), [D190](../decisions/DECISION_REGISTER.md)). Il candidato riusa i moduli non toccati dall'ultima mutation riuscita ([D237](../decisions/DECISION_REGISTER.md)). Superstiti, timeout ed errori bloccano sempre.
- Knip è bloccante nel gate `Node 26` per i controlli non solo documentali. La suite applicativa produce report di copertura completi del perimetro dichiarato, senza soglie percentuali. Benchmark Vitest a richiesta, fuori dal gate e dalla CI ([D190](../decisions/DECISION_REGISTER.md)). Nessun gate automatico sulla CPU remota; comandi, perimetro ed eccezioni in [RELEASE](#qualita-del-codice-e-prestazioni).
- Dopo ogni deploy test il remoto visita soltanto le pagine che provano ambiente, dati e accesso, anche quando la PR non ha eseguito browser ([D192](../decisions/DECISION_REGISTER.md), [D205](../decisions/DECISION_REGISTER.md)); una prova remota fallita si ripete una volta e, se riesce, resta segnalata come instabile ([D159](../decisions/DECISION_REGISTER.md)). Le prove browser della PR e della qualifica seguono la stessa regola, con un limite alle instabilità ripetute ([D271](../decisions/DECISION_REGISTER.md)).
- La testa di `develop` si qualifica da sola dopo i merge: matrice browser IT/EN, mobile/desktop, chiaro/scuro in Chromium e WebKit sulla build test, una visita delle pagine pubbliche sulla build Production locale, con le visite delle aree non toccate riusate per al più sette giorni, mutation pertinente e provenienza ([D269](../decisions/DECISION_REGISTER.md), [D272](../decisions/DECISION_REGISTER.md)). La certificazione per tree vale sette giorni anche se il deploy successivo fallisce; `Promuovi` rilegge comunque via sul commit, provider e migration ([D172](../decisions/DECISION_REGISTER.md)), prepara la build Production con il giorno e la prova sul sito reale prima del traffico, visitando ogni pagina pubblica una volta nei due browser ([D258](../decisions/DECISION_REGISTER.md), [D278](../decisions/DECISION_REGISTER.md)). Nessuna finestra di osservazione a tempo segue il deploy: giorno e readback finale chiudono la promozione ([D288](../decisions/DECISION_REGISTER.md)). Per la pubblicazione conta il diff cumulativo dal commit distribuito ([D280](../decisions/DECISION_REGISTER.md)); senza nulla da distribuire `main` avanza e basta ([D281](../decisions/DECISION_REGISTER.md)).
- Test di repository fanno rispettare le regole di AGENTS: nessuna sigla di milestone, task o fase nel codice, nei test, nelle fixture, nei log e nel copy runtime; fixture solo con host sintetici `.invalid` e senza dati reali; grafo degli import applicativi aciclico, controllato da Oxlint; ogni modulo server ha almeno un consumatore runtime; versioni di Node e pnpm di `mise.toml` coincidenti con `package.json`, da cui le legge la CI.

**Ciclo di una PR.** Una PR pronta si qualifica su una base compatibile, che il ciclo rilegge al merge: i commit entrati nella base nel frattempo non toccano file della PR, documenti esclusi ([D275](../decisions/DECISION_REGISTER.md)), né file globali e non aggiungono migration insieme a lei; altrimenti la PR si aggiorna e si riqualifica. Il push su `develop` riesegue il gate sul tree integrato prima del deploy test ([D195](../decisions/DECISION_REGISTER.md)). Ogni PR ha il proprio ciclo e si mette in fila soltanto per il merge, sotto un blocco fra runner ([D295](../decisions/DECISION_REGISTER.md)). Il comando operativo `release:cycle pr` aggiorna la base mediante merge soltanto quando serve, segue la qualifica già avviata sulla testa senza rimettere la PR in bozza, ripete l'aggiornamento se la base avanza in modo non compatibile durante la qualifica ([D184](../decisions/DECISION_REGISTER.md)), attiva l'automerge e segue CI del commit integrato e, quando il diff distribuisce, ricevuta e readback provider del test; poi elimina il branch della PR. I residui di cicli precedenti si riconciliano a lotti, almeno una volta al giorno di lavoro e a ogni `Promuovi`, conservando lavoro non integrato o in uso. Le migration non additive si approvano nella PR con il digest del loro piano, prima del merge e non dopo un deploy test fallito.

**Proporzione delle PR.** Contenuto, collaudo e chiusura delle PR seguono `AGENTS.md` e il [contenuto delle PR](#contenuto-delle-pr).

Versioni interne `2.0.0-alpha.N`→`2.0.0-rc.N`→`2.0.0`. Non significano beta pubblica. Dopo la pubblicazione della `2.0.0` le funzioni entrano in `develop` soltanto complete e ogni lotto porta una sola versione, senza RC: `2.0.x` per correzioni e piccole funzioni visibili fuori dall'elenco del [§39](../ROADMAP.md#s39), `2.y.0` per le sole funzioni di quell'elenco; le modifiche senza Novità per gli utenti dell'app, interne, della console o del sito pubblico, non hanno versione propria e possono andare in Production da sole, senza tag né release ([D248](../decisions/DECISION_REGISTER.md), [D252](../decisions/DECISION_REGISTER.md), [D302](../decisions/DECISION_REGISTER.md)). Prima di `Promuovi` di una `2.y.0` l'owner prova le funzioni nuove sul test con il proprio negozio, da un elenco preparato dall'agente, e la pubblicazione attende il suo esito; le versioni di correzione non lo richiedono. `CHANGELOG.md` unica storia delle modifiche rilevanti, con le voci dei frammenti di `changes/` fino al giorno della pubblicazione ([D299](../decisions/DECISION_REGISTER.md)); le Novità dell'app (D203) sono le sue parti «Novità» e «What's new», una selezione per l'utente e non una seconda storia tecnica; il giorno entra nella build e `develop` lo riceve dopo la pubblicazione ([D273](../decisions/DECISION_REGISTER.md)); GitHub Release derivata per ogni versione Production, non ogni deploy test. Nessuna riscrittura tag pubblicati per correggere un errore.

`Pubblica`, «Pubblica in Production» e `Promuovi` autorizzano i cicli definiti in `AGENTS.md`, eseguiti secondo il [ciclo operativo](#ciclo-operativo); le decisioni riservate all'owner restano separate dalle normali attività.

`Promuovi` comprende, dopo il readback Production e tag/release riusciti, l'inventario e la pulizia dei branch e worktree temporanei già conclusi, inclusi i residui di cicli precedenti. Il coordinatore verifica per ciascuno PR e contenuto integrato anche quando il merge è squash, stato pulito, commit non pubblicati, file non tracciati e processi o altri lavori che usano il checkout; solo allora elimina branch remoto e locale, libera il worktree e riallinea il checkout principale. Conserva `main`, `develop`, tag, rollback e ogni lavoro non integrato o ancora in uso. Una pulizia non sicura o un passo fallito conservano ricevuta e riferimento di ripresa e restano nelle questioni aperte, senza dichiarare conclusa la pulizia.

Migrazioni versionate, testate su schema/dati rappresentativi, forward-only dove sensato, approccio expand/contract se serve compatibilità. Release manifest collega codice, schema, config e artifact immutabile. Rollback codice automatico se sicuro, altrimenti forward-fix; recovery dati separato. Nessun comando di pubblicazione deve contenere token/PII nelle evidenze.

Il ciclo è vincolato allo SHA e serializzato fra runner fino alla conferma finale ([D285](../decisions/DECISION_REGISTER.md)). Le prove locali del gate e dei browser hanno ricevute indipendenti. La base del lotto viene dalla versione osservata sul dominio e dalla ricevuta provider, anche dopo un ritiro; una ripresa non può dichiarare attivo un candidato ritirato. Giorno e readback finale chiudono la pubblicazione senza guardia a tempo ([D288](../decisions/DECISION_REGISTER.md)). L'urgenza usa soltanto prove già valide. Qualifica automatica senza attese sul runner, campagna completa settimanale, dipendenze verificabili delle aree, shard proporzionati, pulizia locale riprendibile e metriche separate per attivazione e conclusione conservano protezioni e proporzione.

L'avanzamento segue i task della [roadmap](../ROADMAP.md#stato), con prove proporzionate e limiti espliciti. Non duplicare output grezzi né creare un diario delle sessioni. L'agente preserva modifiche dell'owner e worktree non propri.

**Pubblicazione riprendibile e provenienza dell’artefatto.** Legare il via a commit e release manifest attesi. Serializzare le pubblicazioni per ambiente; un workflow più vecchio non deve sovrascrivere uno successivo. Promuovere lo stesso artefatto verificato quando il provider lo consente; se serve una ricostruzione specifica Production, registrare gli input immutabili e verificarne l’artefatto, non chiamarlo automaticamente «lo stesso build testato».

Migration, deploy e tag sono passi con ricevuta e readback separati. Se il deploy riesce ma la creazione della GitHub Release fallisce, la ripresa completa quel passo senza riapplicare ciecamente migrazioni o cambiare versione live. Non pubblicare il tag di successo se smoke/readback non passano. Prima di rollback verificare compatibilità tra versione codice, schema e configurazione, senza recuperare un vecchio DB soltanto per tornare al codice precedente.

Il readback del candidato confronta commit/artefatto, schema e configurazione attesi e verifica gli invarianti applicativi pertinenti alla modifica, inclusi diritti e lavori pendenti bloccanti. Un deploy riuscito o un HTTP 200 non bastano. Provare ripresa dopo interruzione e rifiuto di un candidato superato senza ripetere effetti già confermati.
